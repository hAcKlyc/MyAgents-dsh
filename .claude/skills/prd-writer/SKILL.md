# 对话产出 PRD

把已经收敛的需求讨论**收口成一份能独立活下去、可由用户确认的 PRD**。零上下文的 `/start-dev` 读完后，不需要重新询问产品问题，能找到可信的技术事实并独立形成实施计划。PRD 要把产品契约和技术架构框架定义清楚，但不替开发阶段预写完整代码方案。

记住这份 PRD 的心智模型：**对话给出为什么做、做成什么和用户接受哪些取舍；代码库给出当前事实、职责边界和可复用路径。你的工作是把两者合成一份不会随会话蒸发的交接物。** 只抄对话会得到没有技术地基的愿望清单，只抄代码会失去需求意志。

还要守住交付单位：**一份 PRD = 一次原子交付**。PRD 里写进交付范围的功能、平台、Runtime、迁移、测试、文档与验收项必须在同一次开发周期全部完成，整体验收后统一上线。`/start-dev` 可以按内聚的工程作用域拆开发批次、review 和 commit，但批次不是产品阶段、发布阶段、兼容边界或部分完成定义。

---

## 第 0 步:先判断这段对话熟没熟

PRD 的质量上限,就是它背后那段对话的质量。**先快速扫一遍:核心决策收敛了吗?范围圈住了吗?还有没有悬而未决的产品岔路?**

- 如果还有关键产品或架构岔路未决，先回到 `prd-discuss`，不要用 PRD 替用户补决定。
- 不确定项先分类，不能一律塞进“开放问题”：
  - 会改变产品范围、默认体验、职责归属、权威数据源、通信模式、长期复杂度或完成定义的，先继续讨论或研究，**不能产出可直接开发的 PRD**；
  - 实现中才能验证、但方案方向已定的，写成**本 PRD 内必须完成的验证门槛**，带成功标准、失败处理和验收责任；
  - 明确不属于本 PRD 的，只写进反向边界，不包装成“二期 / 后续期”。如果以后真要做，另起独立 PRD。

plan 之外的新成稿先以 `status: draft` 交给用户核对；尚未收敛的存档稿也保持 draft，不能直接 `/start-dev`。只有用户明确接受当前 PRD 内容后，才能晋级为 `status: ready-for-development`。已有 Stage/Batch PRD 不另造状态体系：按 `specs/prd/plan.md` 使用 `not_started | in_progress | blocked | complete`，并把用户确认、依赖与切换证据写入 plan/PRD ledger。

如果这段对话其实很薄(用户刚起个头就让你写),那这个 skill 的第一步就是**把讨论先聊深**——加载 `prd-discuss` skill(需求讨论模式,那边有完整的聊法和讨论台账机制)带着用户收敛,再回来写。

## 第 1 步:从对话里挖出"意志"和"决策",用用户自己的话

**先看台账**：如果 `specs/prd/_drafts/<slug>.md` 存在，以其中的决策、rationale 和用户原话为首要来源，会话历史只做补充和校验。PRD 通过自检、用户接受当前成稿并进入 `ready-for-development` 后才删除台账；“同意写 PRD”不等于接受尚未看见的成稿。

没有台账时,通读整段会话历史。两种来源都在挖同样两样东西:

**① 用户的需求意志**——他到底想要什么、为什么在意、他的判断和取舍是什么。
- **用他自己的词汇和比喻,别改写成通用 PM 腔。** 如果他说"探针""扔在楼顶""我的秘书""把步骤降到最低",就用这些词。背景章节读起来应该让用户**认出这是他自己的想法**,而不是"被塞进了一个模板"。这是这份 PRD 有没有"灵魂"的关键。

**② 关键决策 + 它的 rationale**——对话里每一次"想清楚了""那就这么定""你说得对,改成 X"的地方,都是一条决策。
- 记的时候**不要只记"定成了什么",要记"为什么这么定、而不是那个更显然的做法、躲开了什么坑"**。这呼应本项目 commit message 的哲学(写 why,不写 what):半年后翻这份 PRD 的人,最常问的就是"他们当时为啥不直接 X?"——你要替他先答了。
- 这些 rationale 往往就藏在对话里的**纠偏和张力**处:用户纠正你误解的那一下、你俩权衡掉一个看似更简单的方案的那一下。那些才是最该被固化的东西,因为它们最容易在没记录时被后人重新踩。

## 第 2 步：核实当前技术事实

PRD 里的技术陈述必须来自当前代码和可靠证据。动笔前：

- 先读 `specs/prd/plan.md` 确认项目阶段、仓库 owner、文档权威与依赖，再按路由读取 `specs/ARCHITECTURE.md`、相关 PRD/RFC、协议、代码、类型、测试、日志和 git 历史。
- 需求涉及现有 Runtime 功能时，以 `myagents-runtime` 的已实现代码和测试为行为/迁移蓝本；优先复制或提取 engine-neutral 实现，不把 Pi AgentLoop、Session、事件或工具注册路径包装进新架构。
- DSH 或外部 SDK/协议以当前锁定版本的公共导出、精确源码和官方一手资料为准；禁止用 package-private `src/*` 或 `dist/*` 路径规避公共 seam 决策。
- 先搜索再引用文件和符号；使用真实名称，不写易漂移的行号。
- frontmatter、章节和交付语义以本 skill 的模板为准。历史 `specs/prd/` 可以提供技术上下文和写作语气，但其中的“一期 / 二期 / Phase / 后续期 / implemented-phase1”是历史记录，**不是当前 PRD 的规范样例**，不得照搬其分期或部分交付结构。
- 若已有 `specs/research/` 报告，把它作为证据来源并建立链接；PRD 只吸收需要用户确认的结论、取舍和架构边界，不复制版本矩阵、完整调用链或候选方案分析。

如果核实结果推翻了讨论阶段的产品或架构前提，停止写作并回到 `prd-discuss`。研究报告和 prd-writer 都没有静默扩大范围的权力。

## 第 3 步:写 PRD——下面这几条是写法红线

### 两种语言寄存器(最重要的一条)

**产品表述用说人话的自然中文;技术事项用规范的专业术语。** 这两件事别串味:

- 讲产品(它是什么、为谁、为什么)→ 自然、口语、用用户的比喻。
- 讲技术(怎么实现、依赖什么、有什么约束)→ 用真实存在的术语:`NSPanel`、`key window`、前缀缓存(prefix cache)、auto-compaction、UIA、`cmd_*`……该叫什么叫什么。

**当你发现自己正要造一个词的时候,停一下。** 那个词要么是个产品想法(那就用大白话讲明白),要么是个技术概念(那就用它真正的名字)。**禁止自造夹生缩写**——`net原则`、`load-bearing`、`arm 焦点`、`edge-dock`、`撞确认闸` 这类中英混搭的生造词,会让读的人卡壳。宁可多写几个字说清楚。

### 展示架构延续性 + 标出红线

讲清这个功能怎么长在既有抽象上、哪些旧分叉应删除或合并，以及会触及哪些架构红线。`/start-dev` 可以决定局部实现，不能再决定系统应当变成什么样。

PRD 必须定义所有会影响产品行为或长期复杂度的结构性选择：

- 状态、资源和策略的职责归属与权威数据源；
- 必须复用的现有主路径，以及禁止建立的平行路径；
- 关键状态和生命周期，以及成功、明确失败、确认不明和资源释放语义；
- 进程、通信、Runtime、权限和信任边界；
- 持久化、迁移和真实外部兼容责任；
- 必须保证与明确不保证的可靠性；
- 允许新增的持久状态、职责主体、协议、队列、重试、恢复、补偿或兼容机制，默认应为空；
- 现有架构无法满足时，必须停止开发并交还用户决定的条件。

不要默认写逐文件修改计划、完整函数调用过程、开发批次或穷举测试实现。只有当某项细节会改变上述边界或验收结果时，才进入 PRD；其余由 `/start-dev` 根据当时的代码决定。

### 明确范围 + 反向边界

写清**本 PRD 一次性交付什么**,也写清**明确不做什么**("反向边界")。反向边界是防止实现过程中范围悄悄膨胀的护栏，不是未来 roadmap：禁止写“一期先做 A、二期补 B”或“本期裁掉 X、转正前再补”。

需求再大，也按一个完整用户结果设计。开发批次只服务于实现、review 和 commit；若产品决定分开发版，每个发布单元分别写成独立 PRD。兼容设计只服务于真实存在的旧客户端、持久数据或外部协议责任，不能由批次间的临时共存状态制造。

## 产出物:放哪、长什么样

**落盘**：先核对 `specs/prd/plan.md` 的 Stage/Batch 文档地图。现有 Stage/Batch 的需求写回其既有 PRD；真正独立的新原子交付才新建 `specs/prd/prd_<version>_<slug>.md`。version 优先从 `package.json` / 当前分支推断；Pre-Batch 尚未创建 `package.json` 时，使用与 plan 一致且未占用的显式版本/名称，不得凭空伪造包版本。关联研究报告放 `specs/research/` 或按 plan 纳入对应 `specs/rfc/`。

**frontmatter**(成稿先进入待用户接受态):
```yaml
---
type: prd
status: draft
created: <YYYY-MM-DD>
updated: <YYYY-MM-DD>
scope: "一段话讲清本 PRD 一次性交付什么、本质是什么、核心价值、以及明确不做什么。"
issue: <来源:产品需求 / issue 号 / 讨论收敛>
research: "<关联的研究报告路径,若有>"
review: "pending user acceptance（产品 / 架构岔路已关闭；等待用户确认当前 PRD 成稿）"
---
```

写完并通过下方“空 session 测试”后，向用户回放：一次性交付范围、反向边界、关键设计决策、实现内验证门槛与发布完成定义，请用户确认当前成稿。对于 plan 之外的新独立 PRD，用户明确接受后，在同一动作中：

1. 把 `status` 更新为 `ready-for-development`；
2. 把 `review` 更新为 `ready for development（用户已确认；产品 / 架构岔路已关闭；当前技术事实与架构框架已核实；实现内验证门槛已写入完成定义）`；
3. 更新 `updated`；
4. 删除已被完整吸收的讨论台账。

在这四步完成前，不得告诉 `/start-dev` 该独立 PRD 已 ready。已有 Stage/Batch PRD 则只有在 plan 依赖满足、用户明确确认 scope、状态与 ledger 同步后才能开始。若用户要求先存未收敛讨论稿，同样保持 `status: draft`，但 `review` 要写真实阻塞项，而不是“pending user acceptance”。

**正文开头必须有一段「执行须知(给空 session 的你)」**——这是让 PRD 能自举的关键。它要告诉一个零上下文的 AI：

- 先读哪些文件（`AGENTS.md` / `CLAUDE.md` 自动加载之外，必须先读 `specs/prd/plan.md`，再主动读本 PRD 引用的 ARCHITECTURE / RFC / 协议 / 研究报告）；
- 本 PRD 是一个原子交付单元，开发批次只用于实现 / 验证 / review / commit，全部完成后统一上线；
- 哪些实现内验证是发布硬门槛；
- 引用为什么给符号名而非行号。

**推荐章节骨架**（按需增减）：
1. **背景与产品定位**：为什么做、为谁、必赢场景是什么。
2. **交付范围与反向边界**：一次性交付什么、明确不做和不保证什么。
3. **产品行为与数据契约**：输入、输出、默认行为和失败体验。
4. **技术架构方案与边界**：职责归属、权威数据源、既有主路径、状态与失败语义、允许和禁止的架构变化。
5. **关键设计决策**：每条说明为什么这样选，以及排除了什么。
6. **验收与发布门槛**：端到端验收、实现中必须验证的技术前提及失败处理。
7. **关联资料**：研究报告、正式架构文档和必要的代码符号入口。

## 收尾自检:过一遍"空 session 测试"

写完别急着交。假装你是一个零上下文的 `/start-dev`，逐项检查：

- 我知道做什么、为什么做和怎么算成功吗？
- 技术陈述是否由当前代码或可靠证据支持，引用是否可定位？
- 职责归属、权威数据源、主路径、状态与失败语义是否明确？
- 所有会改变产品范围、默认体验、通信模式、长期复杂度、发布契约或完成定义的岔路都定死了吗？
- 每个新增长期机制是否由明确需求授权；能否继续复用或删除现有机制？
- PRD 是否只吸收 research 的必要结论，而没有复制完整技术材料或预写实施计划？
- 实现内验证是否都有成功标准、失败处理，并且未通过就不能完成 / 上线？
- 交付范围是否全部在一次开发周期完成并统一上线？有没有“一期 / 二期 / 后续期 / 转正前再补”的暗示？
- 开发批次是否只承担实现 / 验证 / review / commit，而没有制造临时兼容、双写、flag 或受支持的中间态？
- 反向边界是否只表达“不属于本 PRD”，没有偷偷承诺未来一定做？
- 产品表达是否自然，技术术语是否准确，没有自造词？

任何一条答不上来,补回去。
